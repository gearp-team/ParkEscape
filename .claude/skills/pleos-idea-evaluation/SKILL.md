# Pleos 차량 앱 평가 기준

공모전 1차 심사는 차량특화성·창의성·기술 활용성·사업성 네 항목을 보고, 세부 배점은 공개하지 않는다(키트 `contest/CONTEST_SOURCE.md` 심사·시상). 그러나 심사를 통과해도 플랫폼에서 구현할 수 없거나 주행 규제에 걸리면 2차 PT의 동작 시연에서 무너진다. 그래서 공모전 기준 하나만 보지 않고 세 렌즈로 따로 채점한다.

플랫폼 사실은 `references/platform-capability.md`를 기준으로 판단한다. 이 파일에 없는 플랫폼 사실은 키트와 프로젝트 `CLAUDE.md`에서 확인하고, 확인하지 못하면 추측하지 말고 "미확인"으로 적는다.

## 렌즈와 세부 기준

각 기준은 1~5점 정수로 매긴다. 렌즈 점수는 그 렌즈 기준들의 평균이다.

### contest — 공모전 심사 기준

| 기준 키 | 무엇을 보는가 | 5점 | 3점 | 1점 |
|---|---|---|---|---|
| `vehicleSpecificity` | 모바일 대비 차량만의 가치, 주행·정차 맥락과 차량 기능의 결합 | 차량 신호가 없으면 앱이 성립하지 않고, 주행/정차 경험이 다르게 설계됨 | 차량 신호를 쓰지만 빼도 핵심이 대부분 남음 | 휴대폰 앱과 사실상 같음 |
| `creativity` | 독창성, 페인포인트 정의와 해결 방식의 명확성 | 기존에 없는 접근이고 근거 있는 페인포인트를 정확히 겨냥 | 알려진 접근의 의미 있는 변형 | 흔한 아이디어이거나 페인포인트가 막연함 |
| `techUtilization` | Pleos SDK·API를 핵심 기능과 사용 경험에 적절히 활용 | 여러 SDK 신호가 핵심 흐름을 이룸(장식이 아님) | SDK를 쓰지만 부가 기능에 머묾 | SDK를 거의 쓰지 않음 |
| `business` | 타깃 명확성, 사용자 확보, 지속 이용(Retention)·확대 가능성 | 타깃과 반복 사용 이유가 분명하고 확대 경로가 보임 | 타깃은 분명하나 반복 사용 이유가 약함 | 타깃이 막연하고 일회성 |

### feasibility — 구현 가능성

| 기준 키 | 무엇을 보는가 | 5점 | 3점 | 1점 |
|---|---|---|---|---|
| `sdkAvailability` | 핵심 API가 `API_INDEX.md`에 있고 지금 승인된(사용 가능) SDK인지 | 핵심이 Vehicle 조회·NaviHelper만으로 동작 | 핵심 일부가 준비 중 SDK에 기대지만 대체 경로가 있음 | 핵심이 없는 API나 준비 중 SDK에만 기댐 |
| `demoability` | 에뮬레이터·Virtual Console·Fake로 시연할 수 있는지 | 핵심 신호를 모두 Virtual Console로 바꿀 수 있음 | 일부는 Fake 데이터로 대신해야 함 | 시연할 방법이 없음 |
| `buildEffort` | 1차 마감까지 MVP를 만들 수 있는 크기인지(작을수록 높은 점수) | 화면 1~2개, 외부 서버 없음 | 화면 3~4개 또는 간단한 외부 데이터 | 서버·학습 모델·대량 데이터가 필수 |
| `dataRisk` | 외부 서비스·개인 데이터·제휴에 대한 의존 | 차량·내비 데이터만 씀 | 공개 API 하나 정도 | 제휴·유료 데이터·개인정보 대량 수집 필요 |

### safety — 안전·정책

| 기준 키 | 무엇을 보는가 | 5점 | 3점 | 1점 |
|---|---|---|---|---|
| `drivingSafety` | 주행 중 화면·조작이 1~2초 인지 원칙과 규제 비트를 따르는지 | 주행 중에는 상태 표시만, 상호작용은 정차 중에 | 주행 중 간단한 조작이 일부 있음 | 주행 중 주의를 많이 끄는 조작이 핵심 |
| `policyFit` | 앱 카테고리 정합성, 단일 경로 정책, 퍼미션 승인 범위, 성능 기준 | 카테고리가 분명하고 승인된 퍼미션만 씀 | 정책 해석이 필요한 부분이 있음 | 정책과 정면으로 충돌 |
| `privacy` | 위치·주행·탑승자 데이터의 수집 범위와 동의 | 수집 최소화, 차 안에서만 처리 | 동의가 필요한 데이터를 일부 수집 | 민감 데이터를 대량으로 외부 전송 |

## 통과 조건(gate)

아래에 해당하면 점수와 관계없이 `gate: "fail"`로 판정하고 `gateReason`에 조건 번호와 이유를 쓴다. 합산 순위에서 빠지고 "탈락 후보"로 따로 보고된다.

| 번호 | 렌즈 | 조건 |
|---|---|---|
| G1 | contest | 핵심 기능에 Pleos SDK·API를 전혀 쓰지 않는다(기술 활용성 항목을 충족할 수 없음) |
| G2 | feasibility | 핵심 기능이 존재하지 않는 API, 숨김 API(`Vehicle.getGear()` 등), 차량 하드웨어 직접 접근에 기댄다 |
| G3 | feasibility | 핵심 기능이 준비 중 SDK(TTS·STT·FusedLocation·Vehicle 제어)에만 기대고 대체 경로가 없다 |
| G4 | feasibility | 시연에 필요한 신호를 Virtual Console로도 Fake 데이터로도 재현할 수 없다 |
| G5 | safety | 핵심 기능이 주행 중 동영상·게임·긴 글 읽기·키보드 입력을 요구한다 |
| G6 | safety | 내비 카테고리가 아닌데 경로 안내(TBT·음성 경로 안내)를 직접 구현한다 |

## 합산 방식

배점이 비공개이므로 이 하네스가 정한 가중치를 쓴다. 공모전 기준이 순위를 좌우하되, 구현할 수 없는 아이디어가 위로 올라오지 않게 구현 가능성에 큰 비중을 둔다.

```
총점 = 0.55 × contest + 0.30 × feasibility + 0.15 × safety
```

안전·정책 비중이 낮은 이유는 심각한 위반을 이미 통과 조건(G5, G6)으로 걸러 내기 때문이다. 렌즈 하나의 채점이 실패하면 남은 렌즈의 가중치를 합이 1이 되도록 다시 나눈다. 계산은 아이디어 워크플로 코드가 한다.

## 채점 결과 형식

```json
{
  "lens": "feasibility",
  "scores": [
    {
      "ideaId": "I03",
      "criteria": { "sdkAvailability": 5, "demoability": 4, "buildEffort": 4, "dataRisk": 5 },
      "gate": "pass",
      "gateReason": "",
      "rationale": "Seat.registerSeatOccupancy·Door.registerDoorPosition 모두 API_INDEX에 있음(CAR_SEATS, CAR_DOORS). 좌석 점유·도어는 VC Convenience에서 재현 가능. 뒷좌석 area 지원은 미확인"
    }
  ]
}
```

- `criteria`의 키는 위 표의 기준 키를 그대로 쓴다.
- 판단할 정보가 카드에 없으면 2점을 주고 `rationale`에 "정보 부족: {무엇}"을 쓴다. 정보 부족과 나쁜 아이디어를 구분해야 기획 단계에서 보완할 수 있다.
- `rationale`에는 점수를 가른 핵심 근거만 두세 문장으로 쓴다.

## 기획 문서를 평가할 때

`plan-critic`은 같은 렌즈를 기획 문서에 적용한다. 아이디어 카드보다 정보가 많으므로 "정보 부족" 대신 빠진 절을 지적한다. 기획 문서 고유의 검토 항목은 `pleos-app-planning` 스킬의 「검토 기준」에 있다.
