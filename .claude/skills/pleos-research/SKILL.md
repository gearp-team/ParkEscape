# Pleos 리서치·사실 검증

조사 결과는 두 곳에 쓰인다. 하나는 아이디어 도출이고, 다른 하나는 공모전 기획서의 2번(기획 배경), 3번(차량 특화 요소), 6번(타깃·예상 MAU·Retention)이다. 심사위원은 근거 없는 페인포인트와 출처 없는 수치를 감점하므로, 조사의 목표는 많이 모으는 것이 아니라 기획서에 그대로 인용할 수 있는 근거를 모으는 것이다.

## 조사 축

기본 조사 축과 축별 질문·출처 힌트·검색어는 `references/axes.json`에 있다. 오케스트레이터가 이 파일을 읽어 워크플로에 넘기므로, 축을 추가하거나 고칠 때는 이 파일만 고친다.

## 기준일과 최신성

- 기준일은 워크플로가 넘겨준다. 모든 근거에 발행일(또는 조회일)을 적는다.
- 기준일보다 3년 넘게 오래된 수치는 `detail`에 "(YYYY년 자료)"를 밝힌다. 시장 수치는 오래된 값이 최신처럼 보이면 사업성 추정 전체가 틀어진다.
- Pleos 플랫폼 사실의 기준은 키트 수집일(2026-10-24)과 프로젝트 `CLAUDE.md`의 "실제로 확인한 함정"이다.

## 출처 등급

| 등급 | 예 | 쓸 수 있는 곳 |
|---|---|---|
| A | 정부·공공 통계(국토교통부, 한국교통안전공단, 한국교통연구원, 통계청), 법령(국가법령정보센터), 기업 공식 발표·IR, Pleos·42dot 공식 문서(키트 포함), 학술 논문 | 수치, 규제, 플랫폼 사실 |
| B | 주요 언론, 리서치 기관 보고서(요약 기사 포함), 업계 전문 매체 | 추세, 사례, 경쟁 서비스 |
| C | 블로그, 커뮤니티, 앱 리뷰, SNS | 페인포인트의 정성 근거만. 수치 근거로 쓰지 않는다 |

## 키트를 먼저 본다

Pleos는 외부 자료가 거의 없다. 플랫폼 질문은 웹보다 다음을 먼저 읽는다.

- `pleos-claude-kit/CLAUDE.md` — 2장(SDK 가용성), 3장(SDK 치트시트), 4장(플랫폼 규칙), 6장(문서 불일치)
- `pleos-claude-kit/API_INDEX.md` — API 시그니처와 퍼미션
- `pleos-claude-kit/docs/pleos-only/vehicle-app-planning-guide/` — 카테고리, 주행 규제, 성능, 보안 정책
- `pleos-claude-kit/contest/CONTEST_SOURCE.md` — 공모전 원문
- 프로젝트 `CLAUDE.md` — 에뮬레이터에서 실제로 확인한 사실(키트보다 우선)

키트 근거는 `source`에 파일 경로와 절 제목을 적는다(예: `pleos-claude-kit/CLAUDE.md §2.2`).

## 조사 절차

1. 워크플로가 준 축의 질문을 읽는다.
2. 키트에서 관련 내용을 `grep`으로 찾는다.
3. 웹을 검색한다. 한국어와 영어 검색어를 함께 쓰고, 국내 맥락(국내 운전자, 국내 규제, 현대차그룹)을 우선한다.
4. 발견 사항마다 주장, 근거, 시사점을 쓴다. 시사점은 "그래서 차량 앱 아이디어나 기획서에 무엇을 할 수 있는가"다.
5. 결정에 중요한 주장에 `decisionCritical: true`를 단다. 기준은 다음 셋 중 하나에 해당하는 주장이다.
   - 기획서에 수치나 사실로 그대로 인용될 주장(시장 규모, 통계, 사용자 수)
   - 아이디어 채택 여부를 바꿀 주장(플랫폼에서 가능한지, 규제상 금지인지)
   - 서로 충돌하는 출처가 있는 주장
6. 찾지 못한 것과 질문을 좁혀 해석한 내용을 `gaps`에 적는다.

## 발견 사항 형식

워크플로 스키마와 같은 구조로 반환한다. `id`는 `{축 키}-{번호}` 형식이다.

```json
{
  "axis": "user-needs",
  "findings": [
    {
      "id": "user-needs-03",
      "claim": "전기차 운전자의 충전 대기 시간이 길어 차 안에서 보내는 정차 시간이 늘고 있다",
      "detail": "급속 충전 1회 평균 30~40분(2025년 자료). 충전 중 차량 안 대기 비율은 ...",
      "evidence": [
        { "source": "https://...", "title": "...", "date": "2025-08", "grade": "A" }
      ],
      "implication": "충전 대기 시간(정차 상태)을 겨냥한 앱은 주행 규제 없이 깊은 상호작용을 설계할 수 있다",
      "decisionCritical": true
    }
  ],
  "gaps": ["충전 중 차량 내 체류 비율에 대한 국내 공식 통계를 찾지 못함"]
}
```

## 사실 검증

`fact-checker`가 이 절을 따른다. 목적은 주장을 통과시키는 것이 아니라 먼저 깨 보는 것이다.

### 반박 시도 순서

1. 근거 출처를 직접 열어 주장과 같은 내용이 있는지 확인한다.
2. 수치는 값, 단위, 기준 연도, 대상(국내/글로벌, 전체/표본)을 대조한다.
3. 반대 근거를 검색한다. 더 신뢰할 출처가 다른 값을 말하는지 본다.
4. 맥락 왜곡을 확인한다. 글로벌 수치를 국내 수치처럼 쓰거나, 예측치를 실측치처럼 쓰는 경우다.
5. Pleos 주장은 키트와 프로젝트 `CLAUDE.md`와 대조한다. 키트와 다르면 키트가 기준이다.

### 판정 기준

| 판정 | 조건 |
|---|---|
| `confirmed` | 출처를 직접 열어 주장·수치·날짜가 일치함을 확인했고, 출처가 A·B등급이다(C등급은 정성 주장에 한해 허용) |
| `refuted` | 출처가 다른 값을 말하거나, 더 신뢰할 출처가 반대 사실을 보여 준다. `correction`에 고친 내용을 반드시 쓴다 |
| `uncertain` | 출처를 열 수 없었거나, 자료가 오래됐거나, 해석의 여지가 크다 |

확인하지 못한 주장을 `confirmed`로 판정하지 않는다. 검증 단계를 통과한 주장만 리서치 요약에 사실로 들어가기 때문이다.

## 하지 않을 일

- 출처에 없는 수치를 만들거나 반올림해 바꾸지 않는다.
- C등급 출처만으로 수치 주장을 하지 않는다.
- 웹 글의 Pleos SDK 설명을 키트보다 우선하지 않는다.
