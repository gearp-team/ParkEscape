# Pleos 차량 앱 발상

공모전 심사에서 가장 먼저 걸러지는 아이디어는 "휴대폰 앱을 차 화면에 띄운 것"이다. 차량특화성 항목이 "모바일 대비 차량 환경만의 독자적인 가치"와 "주행·정차 맥락 및 차량 기능과의 결합"을 묻기 때문이다. 발상의 출발점은 기능 목록이 아니라 차 안의 순간이다.

## 좋은 아이디어의 조건

아이디어마다 아래 여섯 가지를 스스로 확인한다. 하나라도 비면 카드의 `risks`에 적는다.

1. **차량이 아니면 성립하지 않는다.** 차량 신호(Vehicle SDK)나 경로(NaviHelper), 주행·정차 상태가 핵심 흐름에 들어간다. 이 신호를 빼도 앱이 그대로 돌아가면 차량특화성이 낮다.
2. **누구의 어떤 불편인지 분명하다.** 페르소나와 페인포인트에 리서치 요약의 발견 사항 id를 근거로 붙인다.
3. **지금 쓸 수 있는 SDK로 핵심이 동작한다.** 핵심은 Vehicle 조회(get·register·check)와 NaviHelper로 만든다. TTS·STT·FusedLocation·Vehicle 제어(set)는 준비 중이므로, 쓰더라도 꺼도 핵심이 살아 있는 보조 기능으로 둔다.
4. **에뮬레이터에서 시연할 수 있다.** 핵심에 쓰는 신호를 Virtual Console로 바꿀 수 있거나 Fake 데이터로 대신할 수 있어야 한다. 2차 PT에서 동작하는 앱을 시연해야 하기 때문이다.
5. **주행 중에 안전하다.** 주행 중에는 1~2초 안에 읽히는 정보와 큰 버튼 하나 정도만 둔다. 깊은 상호작용은 정차·충전 대기 시간에 배치한다. 동영상·게임은 주행 중 실행 자체가 금지다.
6. **마감 안에 MVP를 만들 수 있다.** 1차 제출(기획서 + 동작 APK + 시연 영상)까지 남은 기간에 핵심 흐름 하나를 끝까지 만들 수 있는 크기여야 한다. 서버·외부 데이터가 꼭 필요하면 Fake로 대신할 방법을 같이 적는다.

플랫폼 사실(사용 가능 SDK, Virtual Console 신호 목록, 에뮬레이터에서 확인한 동작)은 `.claude/skills/pleos-idea-evaluation/references/platform-capability.md`에 있다. API 이름은 `pleos-claude-kit/API_INDEX.md`에서 `grep -n`으로 찾은 이름만 쓴다.

## 발상 절차

1. **순간을 고른다.** 승차 전·출발 직전·주행 중·신호 대기·정체·주차 중·충전 대기·도착 직후·하차 후 가운데 관점에 맞는 순간을 두세 개 고른다.
2. **페르소나를 겹친다.** 출퇴근 직장인, EV 오너, 아이와 함께 타는 부모, 배달·영업 기사, 장거리 운전자, 고령 운전자, 동승자 등에서 리서치 근거가 있는 사람을 고른다.
3. **차량 신호를 엮는다.** 그 순간 그 사람에게 의미 있는 신호 조합을 찾는다. 신호 하나보다 조합이 독창성을 만든다(예: 좌석 점유 + 도어 열림 + 기어 P → "뒷좌석에 사람이 남은 채 잠금"을 알아챔).
4. **"차가 먼저 알아채는" 흐름으로 바꾼다.** 사용자가 앱을 열어 입력하는 흐름보다, 차량 상태 변화가 앱을 깨우는 흐름이 차량특화성과 안전성을 함께 높인다.
5. **주행/정차 화면을 나눠 적는다.** 같은 기능이 정차 중 화면과 주행 중 화면으로 어떻게 달라지는지 쓴다. 이 에뮬레이터의 주행 중 규제는 동영상·설정 금지(`0x50`)뿐이지만, 지역(예: 북미)에 따라 키보드·긴 글까지 막히므로 주행 중 화면은 최대 제한에서도 쓸 수 있게 설계한다.
6. **시연 시나리오를 쓴다.** Virtual Console에서 어떤 신호를 어떤 순서로 바꾸면 화면이 어떻게 변하는지 3~5단계로 쓴다.
7. **계속 쓸 이유를 붙인다.** 한 번 쓰고 끝나지 않을 이유(매일 반복되는 순간, 누적 기록, 가족 공유 등)를 `retentionHook`에 쓴다. 사업성 항목이 Retention을 묻는다.

## 피할 아이디어

- 경로 안내(TBT·음성 경로 안내)를 직접 구현하는 아이디어: 앱이 내비 카테고리가 아니면 단일 경로 정책에 어긋난다. 경로는 NaviHelper로 내장 내비에 맡긴다.
- 주행 중 동영상·게임·긴 텍스트 읽기·키보드 입력이 핵심인 아이디어
- 숨김 API(`Vehicle.getGear()` 등)나 차량 하드웨어 직접 접근이 필요한 아이디어
- 이미 기본 앱이 하는 일(일반 음악 재생, 기본 공조 조작)을 다시 만드는 아이디어

## 아이디어 카드 형식

워크플로 스키마와 같은 구조로 반환한다. `id`는 관점 키와 번호로 만든다(예: `family-2`). 정리 단계에서 다시 매긴다.

```json
{
  "id": "family-2",
  "title": "뒷좌석 깜빡 알림",
  "oneLiner": "시동을 끄고 문을 잠그기 전에 뒷좌석에 남은 아이·반려동물을 차가 먼저 알려 준다",
  "angle": "family",
  "persona": "영유아와 함께 타는 30~40대 부모",
  "painPoint": "하차 시 뒷좌석 아이를 잊는 사고 위험",
  "evidenceIds": ["user-needs-05", "regulation-safety-04"],
  "coreLoop": ["출발 시 뒷좌석 점유 기록", "도착 후 기어 P·도어 열림 감지", "뒷좌석 점유가 남아 있으면 전체 화면 경고", "하차 확인 기록"],
  "vehicleSignals": [
    { "api": "Seat.registerSeatOccupancy", "purpose": "뒷좌석 점유 감지" },
    { "api": "Door.registerDoorPosition", "purpose": "문 열림 감지" }
  ],
  "naviUsage": "도착 이벤트(onDestinationArrived)로 경고 시점을 앞당긴다",
  "parkedExperience": "하차 체크리스트와 기록 화면",
  "drivingExperience": "주행 중에는 화면을 띄우지 않고, 출발 시 점유 상태 아이콘만 1초 표시",
  "demoScenario": "VC: 좌석 점유(뒷좌석) ON → 기어 D, 속도 30 → 기어 P → 운전석 도어 열림 → 경고 화면",
  "mvpScope": "점유 감지 + 하차 경고 + 기록 1화면",
  "retentionHook": "매 하차마다 자동으로 동작하고 주간 기록을 가족과 공유",
  "businessModel": "무료 기본 + 가족 공유 구독",
  "category": "Lifestyle",
  "risks": ["Seat 점유 API의 area 지원 범위를 에뮬레이터에서 확인해야 함"]
}
```

`vehicleSignals.api`는 `도메인.메서드` 형식으로 쓴다. 예시의 두 API는 실제로 있지만, area(어느 좌석·문을 지원하는지)는 에뮬레이터마다 다를 수 있으므로 카드마다 `API_INDEX.md`에서 이름을 확인하고 area 확인이 필요하면 `risks`에 적는다. `category`는 Maps/Navigation, Mobility Services, Lifestyle, Entertainment, Business, Music/Audio, Kids, Social/Communication 가운데 하나다.
