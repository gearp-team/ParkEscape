# Pleos 앱 기획 문서 작성

기획 문서 하나가 세 사람에게 쓰인다. 심사위원은 기획서 초안(접수양식)을 읽고 네 항목을 채점하고, 개발자는 기능 명세와 SDK 대응표를 보고 구현하며, 발표자는 시연 시나리오대로 2차 PT를 진행한다. 그래서 문서 안의 세 부분이 서로 어긋나면 안 된다. 기획서에 쓴 기능은 명세에 있어야 하고, 명세의 기능은 SDK 대응표와 시연 시나리오로 이어져야 한다.

문서 뼈대는 `references/plan-template.md`를 그대로 쓴다.

## 쓰는 순서

1. **아이디어 카드와 리서치 요약을 읽는다.** 카드의 `evidenceIds`가 가리키는 발견 사항을 `docs/research-digest.md`에서 찾아, 확인됨(`confirmed`) 표시가 있는 것만 사실로 인용한다.
2. **기능 명세부터 쓴다.** 기획서 문장보다 명세가 먼저 정해져야 기획서가 과장되지 않는다. MVP는 1차 제출 전에 끝까지 동작해야 하는 핵심 흐름 하나다.
3. **SDK·퍼미션 대응표를 쓴다.** 명세의 기능마다 쓰는 API를 `pleos-claude-kit/API_INDEX.md`에서 `grep -n`으로 찾아 정확한 이름, 퍼미션, 승인 상태를 적는다. 준비 중 SDK에는 대체 경로를 같이 적는다.
4. **화면·상태 설계를 쓴다.** 화면마다 정차(P) / 공회전(D, 0km/h) / 주행(D, 속도>0) × 1단(portrait) / 2단(landscape)에서 무엇이 보이고 무엇이 숨는지 표로 쓴다. 주행 칸에는 이 에뮬레이터의 규제(`0x50`)에서 보이는 것과, 최대 제한(`0x1ff`, 북미 등)에서도 남는 것을 함께 적는다. 에뮬레이터에서 확인한 규제 동작은 `.claude/skills/pleos-idea-evaluation/references/platform-capability.md` 5절에 있다.
5. **시연 시나리오를 쓴다.** Virtual Console 조작(신호와 값)과 기대 화면을 단계별로 쓰고, 2~3분짜리 시연 영상 콘티를 붙인다. Virtual Console로 못 바꾸는 신호는 Fake 데이터로 대신한다고 밝힌다.
6. **기획서 초안(접수양식 8항목)을 쓴다.** 위에서 정한 내용을 심사 언어로 옮긴다.
7. **일정과 리스크를 쓴다.**

## 기획서 초안 작성 규칙

접수양식 항목은 키트 `CLAUDE.md` 1.3절과 `contest/contest-application-consent.docx`를 따른다.

| 항목 | 심사 항목과의 연결 | 꼭 들어갈 것 |
|---|---|---|
| 1. 한 줄 소개 | 전체 | 누구의 어떤 불편을 차의 무엇으로 푸는지 한 문장 |
| 2. 기획 배경 | 창의성(페인포인트) | 확인된 근거 2~3개(출처 표기), 기존 해결책의 한계 |
| 3. 주요 기능 및 차량 특화 요소 | 차량특화성 | 기능마다 쓰는 차량 신호, 주행/정차에서 달라지는 경험 |
| 4. 주요 사용 시나리오 | 차량특화성·창의성 | 페르소나 한 명의 하루 속 2~3개 장면 |
| 5. 개발 계획 | 기술 활용성 | Pleos Connect 구현 방식, 개발 범위(MVP/PT), SDK·API 사용 계획을 API 이름 수준으로 |
| 6. 기대효과·발전 가능성 | 사업성 | 타깃 규모, 예상 MAU 계산식, Retention 근거, 확대 계획 |
| 7. 참고자료 | 가산점 | 시연 영상·GitHub 저장소 링크 자리, 근거 출처 목록 |
| 8. 숏폼 링크 | 별도 시상 | 자리만 둔다 |

- **예상 MAU는 계산식으로 쓴다.** 예: `대상 차량 수(근거) × 앱 설치율(가정) × 월 활성 비율(가정)`. 근거 수치와 가정을 구분하고, 가정에는 왜 그 값인지 한 줄을 붙인다. 근거 없는 큰 숫자는 사업성 점수를 깎는다.
- **블라인드 규정을 지킨다.** 팀원 실명, 연락처, 소속, 개인 계정 이름을 쓰지 않는다.
- **카테고리를 밝힌다.** 8개 앱 카테고리 중 하나를 고르고 이유를 쓴다. 카테고리와 기능이 다르면 마켓 심사에서 반려된다.
- **주행 중 안전 설계를 기능처럼 쓴다.** 심사위원은 주행·정차 맥락과의 결합을 본다. "주행 중에는 무엇을 숨기고 무엇만 남기는지"는 약점이 아니라 차량특화성의 근거다.

## 기능 명세 규칙

기능마다 다음 칸을 채운다. 개발자가 질문 없이 구현할 수 있어야 한다.

- 기능 id(`F1`, `F2`…), 이름, 단계(MVP / PT / 이후)
- 사용자 가치 한 문장
- 화면과 사용자 동작
- 데이터 소스: API(정확한 이름), 퍼미션, Repository 이름(예: `SeatRepository`)
- 주행·정차별 동작
- 실패·미지원 시 동작(capability 미지원, 에뮬레이터 실패, 퍼미션 거부)
- Fake 데이터(시연용)
- 완료 조건(QA가 확인할 수 있는 문장)

MVP 기능은 3개 이하로 둔다. 1차 마감까지 동작하는 APK와 시연 영상을 함께 내야 가산점을 받으므로, 기능 수보다 끝까지 동작하는 흐름 하나가 중요하다.

## 일정 규칙

기준일(오케스트레이터가 준다)부터 다음 마감까지 주 단위로 거꾸로 짠다. 날짜는 키트 `CLAUDE.md` 1장의 공모전 일정이 기준이다.

- 1차 접수 마감 2026-11-15 23:59: 기획서 + MVP release APK(`apk/` 폴더) + 시연 영상(+ 숏폼은 선택)
- 1차 결과 2026-11-23
- 2차 PT 2026-12-03~04: 동작하는 앱 시연 필수
- 최종 선정 2026-12-18, 전시 2027-02

마감 사흘 전에는 기능 개발을 멈추고 release 빌드·영상·제출 점검만 하도록 버퍼를 둔다.

## 검토 기준

`plan-critic`이 이 목록으로 검토한다. `.claude/skills/pleos-idea-evaluation/SKILL.md`의 세 렌즈와 통과 조건도 함께 적용한다.

| 번호 | 검토 항목 | 심각도 기본값 |
|---|---|---|
| C1 | 템플릿의 모든 절이 있다 | 빠진 절은 BLOCKER |
| C2 | SDK 대응표의 모든 API가 `API_INDEX.md`에 있고 이름·퍼미션이 일치한다 | 불일치는 BLOCKER |
| C3 | 핵심(MVP) 기능이 준비 중 SDK에만 기대지 않는다 | BLOCKER |
| C4 | 기획서 3·5번의 기능이 명세에 있고, 명세의 기능이 대응표·시연 시나리오와 이어진다 | 어긋남은 MAJOR |
| C5 | 시연 시나리오의 신호가 Virtual Console 카탈로그나 Fake 데이터로 재현된다 | 재현 불가는 BLOCKER |
| C6 | 주행 중 화면이 규제 비트를 따르고, 주행 중 핵심 상호작용이 없다 | 위반은 BLOCKER |
| C7 | 사업성 수치에 출처나 계산식이 있다 | 없으면 MAJOR |
| C8 | 일정이 마감에서 역산되고 버퍼가 있다 | 없으면 MAJOR |
| C9 | 실명·연락처·소속·개인 계정이 없다 | 있으면 BLOCKER |
| C10 | 카테고리가 명시되고 기능과 맞는다 | 어긋나면 MAJOR |

판정은 BLOCKER가 0개면 `PASS`, 1개 이상이면 `FIX`다.
